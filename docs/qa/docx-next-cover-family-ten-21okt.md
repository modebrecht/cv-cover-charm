## Scope: ten saved-state applications, no invented DOCX exports

The test matrix is in `tests/fixtures/docx-next/cover-family-ten-cases.json`. ## What the runner actually does

`scripts/docx-next-cover-family-ten.ts` restores each file through the real application project-upload input, visits Letter/CV/Cover, captures effective cover CSS, image crop and badge/shape rectangles, screenshots up to four pages each for Letter and CV in the same app session, reads the actual saved snapshot, builds a diagnostic **default** native model without modifying it, and attempts a normal application PDF download. It records a PDF only if the real app produced the download, with a SHA-256; preflight blocks are recorded as blocks. It checks that export does not mutate local storage and that the project data matches the captured source. Each case gets a manifest; a consolidated manifest explicitly labels this a **Web/PDF reference packet**, not an editable native DOCX acceptance packet.

**No native DOCX is generated by this runner:** the app authorizes authored DOCX only for Brief and Modern. It is prohibited to replace this missing app export with `renderDossierDocx(buildDossierDocModel(...))` and claim it as an application-exported candidate. The existing three-family gating tests remain in place.

## Shared capsule geometry correction (21 October)

The actual Web shape renderer `ShapeElement` uses `border-radius: 9999px`
for a "circle" shape. On a 150 × 130 mm Neon blob, CSS produces a
**stadium / capsule contour**, not an ellipse. The previous native Canvas
rasterizer used `ellipse()`, creating a visible outline mismatch.
The shared `decoration.ts` contour now uses a CSS-equivalent rounded rectangle
with half the shorter side as radius, adjusted for stroke inset. Square circles
remain circles. Gradient stops, opacity, page clipping, saved coordinates and
all editable text remain unchanged.

Likewise, fully rounded photographs with unequal width/height now produce a
native DrawingML `roundRect` with 50% corner adjustment, while square images
continue to use `ellipse`. The authored compositor's two blanket non-square
rejections were removed because the shared shape and image primitives now
represent those geometries. It remains behind the existing template-family
gate; this patch alone **does not enable** Verlauf/Neon/Warm native DOCX.

Added pure/unit assertions for 150×130 and 40×60 contour geometry, two
picture corner behaviours, and authored gradient and picture-frame preservation.
**Not run in GPT-6 Chat:** Bun, screenshot comparisons, real app DOCX/PDF, Word.


## Corrected image-height anchor parity

The same Web `resolveLayout()` used by Cover and the PDF view previously
reserved height for `photo` and `shape` only. A user-inserted `image` has
the same real rendered height of `width × ratio`, but contributed **zero**
to `follows` / `above` geometry when the image had no text lines. The
authored native compositor already reserved that image height, creating a
Web-versus-Word position discrepancy. The shared Web resolver now includes
`image`. A regression test checks a 24 × 36 mm image followed with 3 mm gap,
requiring the next field to start at 49 mm and the source to remain unchanged.

This corrects a real source-level mismatch, but is not a new app export or
Word acceptance result. Users' explicit coordinates and links still win.


## Default flow badge width — shared change, not family release

The generic native `flowingElementBox` previously used the full authored
field width as the painted table width for every one-line date badge (historical
Verlauf 166 mm, Neon 110 mm, Warm 164 mm). It now applies one shared bounded
width reservation using **existing `nativeTextWidthMm()`** plus the authored
horizontal padding and 3 mm Word font fallback allowance, capped to the
original width. It applies only to single-line background badges with no explicit
user-saved `w` override. Multiline, empty and manually widened badges retain
the old bounds; all semantic text stays native/editable.

This is a **conservative Word font reservation**, not fresh browser `measureText`
or round-corner acceptance. Expect a smaller and closer default native pill,
not pixel-identical Web/Word styling. The actual native and Word screenshot
must decide the final result. Tests have been authored for three families and
manual-override preservation but **not executed** in Chat.


## Shared horizontal placement of compact date badges

A Web badge lives **inside** its source-wide text field, respecting the saved
field's left/center/right alignment. After shrinking a 166 mm native table to
a content reservation, preserving only its old left inset would place the
Verlauf and Warm badges too far left. `nativeFlowBadgeIndentMm()` now computes
the intrinsic box's offset within the authored original field and safely
clamps it to the native content region. It retains the original inset when
the saved width was explicitly overridden, or when no content-fit was applied.
The three-family regression cases exercise center/left placement, including
right alignment and manual width.


## Editable native initials when no cover photo is uploaded

The three currently gated families now opt into a **shared native-flow photo
placeholder** via the declarative `nativePhotoPlaceholder` capability. If the
saved photo field is visible but contains no image, the default composer adds
the real initials (for example **LM**) as native editable text
(`cover.photo.initials`) in a bounded table at the original photo field's
position in the semantic order. The source-saved width, color, palette slot,
font-weight and visibility determine its styling. A real uploaded photo retains
the original image path without duplicated initials, and an explicitly hidden
photo stays hidden. Existing CV and Letter models are untouched.

The table background and border are **rectangular**, so this does not claim to
reproduce the Web's circular border in desktop Word. Circle/position parity and
save/reopen remain a **closed visual acceptance gate**. Only Verlauf, Neon and
Warm/Freundlich enable this capability; this is a shared mechanism rather than
three separate per-template renderers. Unit tests were added but not run here.
